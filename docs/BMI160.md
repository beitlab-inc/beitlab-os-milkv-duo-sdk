# Standalone Duo S with a BMI160 on J3

[`beitlabduino_bmi160_j3`](../examples/platformio/beitlabduino_bmi160_j3)
uses a **standalone Milk-V Duo S**, an external **BMI160 module**, and
the **3.3 V J3 header**. The robotics carrier must be disconnected.
It runs on the C906 through beitlabduino setup()/loop() on the existing
OS image; no Linux rebuild, separate Linux I²C driver or pinmux command
is required. The existing carrier BMI323 examples keep their own profile.

## Wiring

Wire with power off. Use a module whose supply and I²C logic support 3.3 V.

| BMI160 module | Duo S J3 connection |
| --- | --- |
| VCC / 3V3-compatible VIN | **Pin 1 — 3V3** |
| GND | **Pin 6 — GND** |
| SCL / SCK | **Pin 3 — B20, I²C4 SCL** |
| SDA / SDI | **Pin 5 — B21, I²C4 SDA** |
| CS / CSB, if exposed and not already strapped | **3V3**, held high before power-up for I²C |
| SDO / SA0, if exposed | GND for **0x68**, or 3V3 for **0x69** |
| INT1 / INT2 | Leave unconnected; acquisition uses polling |

J3 uses 3.3 V signals. Do not use 5 V pull-ups or the J4 1.8 V pins for
this example. Check the module's labels and existing pull-ups/straps;
SDA and SCL need pull-ups to 3.3 V. Keep wiring short. The driver checks
only the two supported addresses and requires chip ID **0xD1** before
writing sensor registers. Other sensor models are not initialized.

Pin evidence: [Milk-V Duo S J3 pinout](https://milkv.io/docs/duo/getting-started/duos#header-j3).
The [Bosch BMI160 datasheet](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi160-ds000.pdf)
describes the CSB/SDO straps and sensor supply limits; check the breakout
board documentation for its VIN/regulator connections.

## Build, upload and view

On your Linux x86_64 PC (or WSL2), from the repository:

```sh
git pull --ff-only
scripts/fetch-freertos.sh             # once if not already completed
export PIO_DUO_HOST=beitlab-milkv-duo.local  # use your working SSH host/IP
export PIO_DUO_USER=beitlab
cd examples/platformio/beitlabduino_bmi160_j3
pio run -t upload
pio run -t rtmonitor
```

Expect the `standalone BMI160 profile duos_bare_bmi160_j3` banner,
followed by `BMI160 ready` with the detected address and then readings.
Output is shaped like this **illustrative example**, not a captured
hardware measurement:

```text
RTD: bmi160 a_mg=12,-8,998 g_mdps=122,-61,0 temp_mC=24500
```

Each group contains sensor X/Y/Z. 1000 mg = 1 g, 1000 mdps = 1 degree
per second and 1000 mC = 1 °C. The sensor runs at 100 Hz with ±4 g and
±2000 °/s ranges; the task prints the latest sample about every 100 ms.
No calibration, robot-axis rotation or orientation fusion is applied.
At rest, acceleration should contain roughly one g and gyro readings
should be near zero. Invalid/unavailable data is not replaced with zeros.

For physical serial, use a **3.3 V USB–TTL adapter on J22, 115200 8N1**:
adapter RX to board TX, with common ground. Do not connect adapter power.
The same output has `RT:` prefixes and shares the Linux console. SSH
monitoring needs no adapter. Ctrl-C stops the viewer; sampling continues.

## Reuse the API

The project explicitly selects the standalone profile and libraries:

```ini
custom_profile = duos_bare_bmi160_j3
custom_libs = beitlabduino duos_i2c4 beitlabduino_bmi160
```

Include `beitlabduino.h` and `beitlabduino_bmi160.h`. Call
`bl_bmi160_begin()` from setup() or loop(); it returns 0 on success and
-1 on failure. `bl_bmi160_address()` returns the selected address while
initialized. `bl_bmi160_read(&sample)` returns:

| Result | Meaning |
| --- | --- |
| `BL_BMI160_SAMPLE_READY` (1) | Valid `bl_bmi160_sample_t` in mg/mdps/mC |
| `BL_BMI160_NOT_READY` (0) | Wait for a new sample; output unchanged |
| `BL_BMI160_ERROR` (-1) | Error; output unchanged, call begin() again |

Print only when the result **equals** `BL_BMI160_SAMPLE_READY`. Fields
are `accel_mg[3]`, `gyro_mdps[3]` and `temperature_mc`. The example uses
delayed retries and reinitializes after a second without fresh data.

To share one sketch with the robotics carrier, use the board-independent
`bl_imu_*` API instead: the `milkv` environment of
[`beitlabduino_imu`](../examples/platformio/beitlabduino_imu) reads this
BMI160 (`pio run -e milkv -t upload`), and its default `robotics_board`
environment reads the carrier BMI323. See [IMU.md](IMU.md#beitlabduino-api).

## Ownership and validation

The new profile inherits `duos_bare`, never a carrier profile. It grants
only I²C4 targets 0x68/0x69 and the B20/B21 peripheral route. Those pads
remain unavailable as general GPIO outputs. Linux console/network/storage
permissions stay reserved. Do not select this profile on a robotics
carrier, where B20/B21 are connected to other hardware.

The shared bounded polling transport selects J3 from the compiled profile.
If a previous program left I²C4 on J4 B1/B2, it disconnects only those old
I²C mux selections as inputs. It does not drive GPIO data or change
unrelated pin functions, system clocks/resets, PWM or IRQ configuration.
The existing carrier examples retain their J4 routing and 0x68-only grant.

BMI160 accesses use byte registers with no I²C dummy bytes. Initialization
uses individual writes and minimum post-write delays, verifies ranges
and power modes, and leaves both interrupt outputs off. Delays include
an extra scheduler tick to preserve minimum timing. Readout decodes the
gyro-before-accelerometer burst and checks data readiness and temperature.

Builds, remoteproc ELF checks and host protocol/policy/fault tests pass.
On robot-72 (OS 0.5.0, GY-BMI160 module on J3) the `milkv` environment of
`beitlabduino_imu` reads plausible samples at 10 Hz: about 0.95 g total
acceleration at rest, gyro under 1 °/s, 25.6 °C. Bus timing and a serial
capture on J22 remain pending.
Diagnostics such as `not found at 0x68/0x69` should first prompt checks of
power, shared ground, J3 pin numbers, pull-ups and CSB/SDO straps.

`I2C4 init error=-2` means controller shutdown timed out **before the sensor
probe**, so it does not establish that the module is missing or miswired.
The driver attempts one bounded controller-local abort if master activity
prevents shutdown. It enables the controller before issuing ABORT and does
not change routes until shutdown succeeds. No system clocks/resets or GPIO
bus recovery are used. Persistent faults report `en`, `state` (enable status)
and `status` registers in hexadecimal; retain the full line for diagnosis.
Other transport errors are -1 (profile denied), -3 (transaction aborted),
-4 (controller identity/FIFO error), and -5 (invalid argument).

In Studio, use **Build**, then **Upload & run** to pick up library fixes;
uploading an existing build uses its original library code. No sketch edit,
student-installed tool or image reflash is required for this driver update.
On robot-72 (OS 0.5.0), ABORT self-cleared without releasing an empty-FIFO
master. One read-only RESTART/READ/STOP at its already-selected, profile-allowed
seven-bit address released SCL and allowed shutdown. The driver uses that
bounded fallback if ABORT does not release the master. It never writes sensor
register data or changes the target for recovery. Invalid/disallowed targets,
non-master operation and insufficient FIFO space are refused.

That recovery sequence was tested on robot-72. The held master it released
was caused by the transport itself: every multi-byte read stalled, because
the driver waited for each received byte before queuing the next read
command, and the controller completes a byte only once the next command
(or STOP) decides its ACK/NACK. One-byte identity reads worked, so the
chip ID 0xD1 was found while configuration read-back timed out
(`i2c=-2 reg=40`, fault `stage=5 status=27`). The transport now keeps one
read command queued ahead, and initialization and sampling succeed.

Failures now name the I²C code and register, then add a fault line:
`stage` is where the transfer stopped (1 shutdown, 2 enable, 3/4 TX space,
5 waiting for a received byte, 6 STOP, 7 master idle), followed by the
controller's status, raw interrupt, FIFO levels and enable status.
